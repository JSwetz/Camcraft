# CamCraft CL Intermediate (`.cnc` role) — format v1

Provenance: our own format, designed here. Only its *role* matches the
Fusion 360 post architecture (an intermediate the post script consumes,
record by record, through a lifecycle hook set) — specced from
Autodesk's published post-processor documentation, behavior only, per
the Clean-Room Protocol. No text from any vendor file is reproduced
here; the grammar is ours.

The intermediate is generated by `app::post::dump` from a toolpath
plus its resolved context (`app::post::Dump`), serialized by
`app::post::cnc::serialize`, and read by `app::post::cnc::parse`. It
is line-oriented, deterministic (µm integers for geometry, 6-decimal
fixed for parameter reals), and carries no timestamps — the same law
as the `.cl` golden dumps, of which this is a superset: a file with no
`HSMW-CNC` magic line parses by the legacy `.cl` rules, so every
committed golden is a legal post input.

## Records

| line | meaning |
|---|---|
| `; HSMW-CNC v1` | header; its absence means legacy `.cl` input |
| `PARAM <name> <value…>` | one named parameter; the value is the rest of the line (strings may carry spaces) |
| `WARN <text…>` | a verification warning attached to the path (the rest of the line) |
| `TOOL <n> <name…>` | the tool block: library number (1-based) + name (rest of line) |
| `SECTION [label]` | an operation's record span begins |
| `ENDSECTION` | the span ends |
| `Rapid X <i> Y <i> Z <i>` | G0 move to, µm integers |
| `Feed X <i> Y <i> Z <i> F <i>` | G1 feed move, F = mm/min × 1000 |
| `Plunge X <i> Y <i> Z <i> F <i>` | G1 at the plunge feed |
| `Arc CW\|CCW X.. Y.. Z.. F.. I.. J..` | planar arc; I J = absolute center |
| `CYCLE <TYPE> X.. Y.. Z.. [R.. ENTRY.. Q.. P.. F.. AT..]` | one canned cycle |
| `PART LOAD [ADVANCE <µm>]` / `PART UNLOAD` | a part lifecycle event: `dump` brackets each section with them; ADVANCE rides the LOAD alone (the bar's next bite, µm) |
| `PART TRANSFER <from> <to>` | the handoff step of the same family: station `from` (1-based, the order the machine file states its spindles) hands the part to station `to`; both operands required, a missing or zero-station number refuses by name |
| `START X <i> Y <i> Z <i>` / `END` | legacy `.cl` position lines: consumed silently (END ends the record span) |

`CYCLE` TYPE ∈ SPOT DRILL PECK DEEP TAP BORE BACKBORE. Word meanings
match the `.cl` v3 `; CYCLE` marker the M1.6 goldens use, and one
parser reads both: X Y center, Z (or `BZ`) bottom, R (or `RZ`)
retract/feed plane, `ENTRY` entry plane, Q (or `PECK`) peck, P (or
`DWELL`) dwell in ms, F cutting feed × 1000 (`dump` synthesizes it
from the group's first cutting move; legacy markers carry none, so
the property is `null` and the post keeps the modal feed), AT the
first move of the hole's chain group (defaults to the cycle's own
position in the file). A bare number
(`1000`), a spaced key (`X 1000`), a joined key (`X1000`), and a
separated key (`X:1000` / `X=1000`) are the same word to the parser,
so the canonical spaced writer, the compact joined form, and the
legacy positional form all round-trip.

## Rotary address words (stage D)

A motion record may command the tool orientation with keyed words
`A <i> B <i> C <i>` (millidegrees, ×1000, the same integer discipline
as the length words): `Rapid X 10000 Y 0 Z 5000 A 40000 B 0 C 0`.
The values are ABSOLUTE commanded angles, and they locate the TOOL
TIP — no pivot compensation is implied by the stream; a post that
keeps the machine prismatic must refuse such a record, never
re-interpret it. The law at the parser: a tilted record states all
three letters (an unstated one reads `0`), and every in-app `dump` of
a prismatic toolpath omits them entirely — absence is the ordinary
case, and the properties `A`/`B`/`C` are then not present at all,
which is how a script tests for tilt (`has(properties.A)`).

## Parameter names

The engine publishes every PARAM, both WCS slots, and a set of fixed
machine/position keys into the script's `properties` object. Names
follow the CAM-intermediate convention (public documentation,
behavior only):

| name | meaning |
|---|---|
| `StartX` `StartY` `StartZ` | current point before the record (mm) |
| `X` `Y` `Z` | record end point (mm; cycles: center XY, bottom Z) |
| `A` `B` `C` | commanded tool angles, degrees — ABSENT unless the record carries the words above |
| `IJKIncrement` | absolute arc center, mm (from `Arc` I J) |
| `FeedRate` | in-feed, mm/min (from F × 0.001) |
| `FeedReference` | `surface` when set |
| `ToolNumber` `ToolName` | from `TOOL` |
| `SpindleSpeed` | rpm (PARAM) |
| `WorkOffset` `OriginX` `OriginY` `OriginZ` | WCS slot + machine origin (PARAMs) |
| `StockXYLeft/Right/Front/Back` `StockZTop` | stock bounds (PARAMs) |
| `ClearancePlane` `RetractPlane` `TopOfStock` | plane heights (PARAMs) |
| `OperationName` `ToolDiameter` | op identity (PARAMs) |
| `command` | per motion/cycle record: `Rapid` `Linear` `Circular` `Drilling` (the `onCommand` argument); part events set `PartLoading` / `PartUnloading` / `PartTransfer` for their dedicated hooks and never reach `onCommand` |
| `Advance` | the `PART LOAD` ADVANCE in mm (present only on loads; an unload's properties carry no `Advance` key at all) |
| `From` `To` | the `PART TRANSFER` stations, 1-based (present only on transfer events) |
| `CircularDirection` | `CW` / `CCW` (arcs) |
| `CycleType` | the `CYCLE` TYPE token (cycles) |
| `EntryZ` `Q` `P` `FeedRate` | cycle entry plane, peck mm, dwell s, cutting feed mm/min (`null` for legacy markers) |
| `LinearMovementIncludeOpts` | `{L:[1]}` on plunges (the skip-the-rapid convention) |

## The hook contract

`app::post::js::PRELUDE` (original, shipped in-repo) gives every script:

- `properties` — one object per record, as above; `W` an alias
- `currentPosition` — `{X, Y, Z}`, live
- `machine` — the `.mch` flattened: `rapidRate`, `feedRateMax`,
  `spindleMax`, `coolants[]`, `rotaries[]` (letter + stated direction
  + travel in degrees, geometry never speeds), and `rtcp` — a
  geometric judgment, true when some rotary states a direction that
  is not the Z column (an A about X tilts; a spindle-column C turns
  in plane). A script may output RTCP modes only when `rtcp` is true;
  a tilted record on a `rtcp:false` machine is a counted refusal.
- writes: `writeln(s)`, `write(s)` (appends to the open line),
  `writeBlock(...parts)`, `writeWord(w)`, `writeAddress(letter, value, dp)`,
  `writeComment(s)`, `writeBlankLine()`, `writeOutput(...)`
- `getProperty(k)` / `setProperty(k, v)` — the `properties` object
- `message(s)` — counted warning, not text
- format helpers `formatUnit` / `formatMotion` / `formatFeed`
- `onComment(s)` — default: `writeln(s)`
- `onPartLoading()` / `onPartUnloading()` / `onPartTransfer()` —
  defaults write the intent as a comment (`(PART LOAD [ADVANCE <mm>])`,
  `(PART UNLOAD)`, `(PART TRANSFER <from>-><to>)`); a script with a
  real feeder or handoff dialect overrides them as it would any hook
  (the engine invents no M-code it was not given)
- `setLanguageVersion(_v)` — accepted and ignored (the engine decides
  semantics, not the script; a reference-era pragma kept harmless)

The engine calls, in order, if the script defines them: `onOpen`,
`onParameter(name, value)` (once per PARAM; `onSpindleSpeed` follows
the `SpindleSpeed` PARAM), `onToolChange(number, name)` (once per
`TOOL`), `onSection` / `onSectionEnd` (one per span), then per
record: `onCommand(name)` — a literal `false` return
swallows the record, and the swallow is counted, never silent —
else the kind hook: `onRapid`, `onLinear`, `onCircular`, or
`onPlunge` for plunges when the script defines it (else `onLinear`);
cycles fire `onCycle`, `onCyclePoint`, `onDwell(seconds)` when the
dwell is positive, then `onCycleEnd`. Part events are lifecycle, like
`SECTION`: `onCommand` never sees them — `onPartLoading` /
`onPartUnloading` / `onPartTransfer` is the whole contract. `onRadiusCompensation` is
reserved (never called in 0.1.0 — the Fanuc post runs G40). `onClose`
ends the run; its lines belong to no record.

A parsed stream is normalized to program order before the hooks
start: legacy goldens append their `; CYCLE` markers after the
chain, and the driver re-seats each cycle just before its AT-anchored
move (idempotent on `dump` output, which is written in program
order). Record indices — `line_map` and `AT` — refer to this
normalized stream.

`app::post::engine::run` returns the program text, a `line_map`
(program line → record index, `None` for header/footer lines), the
`blocks` trace, the counted `warnings` (stream `WARN`s plus every
`message()` — a `WARN` also voices through `onComment`), and the
`swallowed` count. Warnings block the in-app post (the validation
gate, M1.7b); the CLI prints them and still succeeds — it is a
developer tool.

## The block trace (stage D)

`blocks` is the run's block-by-block story: one `TraceBlock` per
record that wrote lines (`record` = its index in the normalized
stream, `label` = a human-readable echo of the record, `first..last`
= half-open program-line range), plus a `header` block (`record`
`None`) for what `onOpen` wrote and an `end` block for `onClose`. A
record the script swallowed by returning `false` appears with an
empty range and a `(no output)` suffix — loss stays visible. Records
that legitimately emit nothing (a `PARAM` the post only stores, the
`TOOL` this post prints inside its preamble) get no block; the trace
reads as the program, not as the stream echoed back. `post --trace
<file>` writes the excerpt (each block as a `; [record N] label`
header over its lines) and the viewer shows the same blocks beside
the listing; clicking a block centers its first line.
